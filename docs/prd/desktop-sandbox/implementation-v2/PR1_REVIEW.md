# mini-sandbox PR #1：设计评审与对抗性比较

日期：2026-10-23。评审对象：`mingmingtsao/mini-sandbox` PR #1 的早期设计快照 `54c0e6f3d9541b47f9ee1fd3b363ef63b813fd28`；#1 已合并，此快照不代表全部合并后修订。

**结论：保留已合并的 #1 为历史产品设计；本文对其早期设计快照提出修订与对抗推演，不代表已证实合并后实现存在漏洞。当前实施基线由 FINAL_SPEC.md 定义，本页保留原始设计评审记录。**

本次阅读了产品定位、模块、接口、界面文档、已有 REVIEW，以及原型的关键权限/状态/自检逻辑；比较对象为此前的前期 macOS 沙箱实施方案 v1。这是静态设计审查和桌面对抗推演，不是应用渗透测试。PR 自述仅完成资料与原型语法检查，没有应用功能测试。验收条件见 ACCEPTANCE.md。

## 1. 保留的设计资产

#1 的价值不只是页面草图：它已经把安全翻译为用户任务。保留“账号连接—运行前检查—工作台—结果/活动记录”的主线、每项权限的后果描述、保存用户当时所见措辞的 ApprovalSnapshot、拒绝扩权的路径、MCP 与 Agent 分别授权，以及失败时不能退回宿主裸跑的原则。

已有 REVIEW.md 的 R01–R12 大多成立。下面不把已有发现冒充新发现，而是补充攻击假设、执行条件和确定性裁决。这里的 P0/P1 表示设计修复优先级，不是已确认的代码漏洞等级。

## 2. 主要发现

### F01 / P0：秘密“引用”不等于秘密不进入不可信域

**证据：**01“决策一”把数据库连接串、SSH 私钥等送入 guest 进程内存，自定义 Provider 自动采用这条路径；同文“决策二”的否决条件又禁止 guest 持有能访问外部的原始凭据。03 C.2、04 首次引导沿用相冲突的承诺。已有 R02 已指出这点。

**反例：**进程若必须读取秘密才能工作，它也能把读到的内容交给模型或写入输出；mlock 防止页被换出，不阻止拥有该内存的进程读取它。单向 vsock 只限制注入通道方向，不限制秘密接收者的其他输出。[W8]

**裁决：**删除自动 memory-inject 兜底。比赛实施基线采用严格模式：第三方原始长期凭据不进入 Agent VM，也不进入任意不可信本地连接器。凭据可由宿主发送给用户绑定的受信上游服务；这些服务是该凭据的受信接收方。必须自己消费真实密码/签名密钥且无法适配的第三方程序，标为不支持，不能暗中降级。未来受信连接器的例外需另立安全配置与审批，不能沿用严格模式承诺。

### F02 / P0：风险标签正在被用作扩权机制

**证据：**02 M5 输入为“未经批准”的请求，但低风险静默放行；02 全局不变式要求未经 M3 批准不得执行；03 verdict 包含 silent-allow-low-risk。已有 R01。

**反例：**用户取消某项基础能力后，执行方仍以“低风险”为由放行，用户拒绝失效。

**裁决：**风险等级只影响提示方式，不产生授权。缺失授权默认拒绝，显式拒绝优先。Agent 在沙箱内执行进程是明确列入运行模板的基础能力，而不是伪装成用户可取消、实际上又自动恢复的安全开关。严格区分沙箱内能力与宿主/外部资源能力。

### F03 / P0：同一 guest 的进程隔离，不足以支持“整个 guest 失陷仍互相隔离”的承诺

**证据：**01 架构图将 Agent 和 MCP 放在一个 Linux guest，D4 以独立进程组与 PID/mount/net namespace 实现隔离。

**反例：**若威胁模型包括初始命名空间的特权进程或 guest 内核被控制，就不能再依赖该内核维护两者隔离。这里并不是说受限 user namespace 中的 root 自动等于宿主或 guest 的全权 root。

**裁决：**不同敏感信任域用不同 VM。无秘密、只处理同一工作区的辅助工具可以与 Agent 同域，但不得再宣称彼此有独立安全边界。需要独立授权的本地 MCP 放独立连接器 VM；凭据仍由宿主管理。宿主依据自己创建的 VM/连接对象识别主体，不信任 guest 自报的 workloadId 或 sessionId。

### F04 / P0：允许某工具/域名，不等于限制其实际资源与副作用

**证据：**03 A.1.3/C.1 主要给出工具名、风险和确认开关；网络按主机准入，缺少完整资源/动作执行模型。

**反例：**允许 GitHub 域名并持有可写身份的连接器，可以绕开工具名限制直接调用写 API；一个名叫 read 的工具也可能有写副作用。远端 MCP 若本就持有广泛权限，其内部行为更不能由客户端过滤 tools/list 约束。

**裁决：**目录中每个安全声明对应真实执行机制：上游最小权限账号/令牌、受信服务适配器的资源与动作校验、必要时的单次审批。工具描述和 readOnlyHint 不是授权事实。通用 MCP 代理只承诺限制发出的协议请求；只有经过适配和验证的服务才能进一步宣称“只读”“仅指定仓库”。任意远端 MCP 不自动成为受信凭据接收者。

### F05 / P0：授权对象缺少一次运行与一次动作的完整绑定

**证据：**03 B.2.3/B.2.4 主要绑定 workloadId，expiresAt 可选，裁决缺少 runId/requestId、具体参数承诺和消费语义。Policy、Workload 的权限重叠。已有 R07、R08。

**反例：**旧实例的迟到确认授权新实例；审批后替换参数；撤权后重放；修改 selector 或账号绑定却复用旧批准。

**裁决：**区分请求、产品上限、用户授予和运行快照。每次运行铸造新的 RunGrant；每次敏感操作铸造一次性 PendingAction。审批绑定实际请求字节对应的规范化内容、服务、资源、运行 epoch、截止时间和 nonce。停止先撤权再停 VM。已发到上游的副作用可能结果未知，不作可回滚或 exactly-once 承诺。

### F06 / P0：审计可观测性与“挡下全部攻击”的界面叙事不匹配

**证据：**03 B.3 说文件越界在挂载层失败、不到 Broker；事件由 guest 上报。04 工作台又显示逐次文件访问与“目前没有任何越界尝试”。已有 R11。

**反例：**guest root 可以关闭或伪造上报。访问 guest 中不存在的 ~/.ssh 只证明那个路径不存在，不自动证明系统记录到了对宿主真实密钥的访问。Broker 拒绝计数为零不能推导没有攻击。

**裁决：**强制分层：宿主执行点产生的审计是可用于验收的证据；guest 行为事件只是未受信诊断。界面改为“网关已拒绝 N 次请求”；零值改为“当前未记录到网关拒绝”，不暗示覆盖所有系统调用。宿主未共享文件的不可达性由专门 canary 测试验证，不靠演示路径或盾牌计数替代。

### F07 / P1：原型把“逐项确认”做成了“必须全选”

**证据：**prototype.html 880–890 的 syncReview() 在高风险项未全部勾选时禁用运行；04 首次审查同样要求勾满。与02逐项裁剪冲突。已有 R05。

**裁决：**批准选择的子集，不强迫批准全部请求。必要能力未授权时应准确显示功能后果，例如“未连接模型，只能运行离线任务”，而不是让用户以为联网 Agent 已可用。默认采用“最小够用模板”，不是刻意删掉必需账号再依靠反复失败补授。

### F08 / P0：文件默认保护和运行生命周期会因 UI/性能发生降级

**证据：**01/03 默认 CoW；prototype.html 570–581 默认选中直接读写。01 性能预算允许热启动慢时默认切换会话复用。已有 R06、F04。

**裁决：**首版固定“导入副本—沙箱修改—审阅—导出新目录”；不共享宿主可写目录、不覆盖原项目。无预热池、无持久运行模式、无因为慢而改变残留语义的自动降级。停止撤权与结果保留分开：用户尚未导出的结果可以受限保留，但不能仍具备外部权限。

### F09 / P1：schema 字段不存在不是保密的证明

**证据：**03 A.1.2 声称字段不存在无从绕过，但 runtime.command/args 等仍可携带任意字符串。02 M2 还要求秘密最多只在一个进程内存，和 Broker/代理/系统库流转不符。

**裁决：**SecretRef 无 value 是良好接口设计，但仍要做入口、日志和出口保护。不承诺扫描器识别所有秘密，不承诺 Swift/系统库的所有副本可瞬时清零。对长期凭据的强保证建立在不向不可信域投递，而不是字符串字段、掩码或零化口号上。

### F10 / P1：P0 不是可使用产品，范围却同时扩到云迁移

**证据：**02 的 P0 不含 M2/M5/M6；模型认证和最小权限主路径却需要这些能力。M7 增加 OCI、K8s、云主机、漂移检测。已有 R04、R12。

**裁决：**首个完整里程碑必须有最小凭据、策略、审计、运行、停止和结果能力。高级审计 UI 可后置，审计机制不能整模块后置。本次移除云投递、计费、跨平台和多种秘密源的实施排期；保留将来扩展点，不做空壳界面。

### F11 / P1：生产“原样迁移”及竞品独占性没有成立

**证据：**03 A.2.2 允许 CoW、MCP过滤缺失，代理注入降为内存注入；01 又承诺安全边界原样迁移。该表将 NetworkPolicy+FQDN 标为通用等价能力，但标准 Kubernetes NetworkPolicy 是 L3/L4，FQDN/L7 需额外实现与验证。[W5]

Docker Sandboxes 已有 microVM、宿主凭据代理、MCP Gateway；这三个组件不能作为独有发明。[W4] 这里不据此断言整个产品没有价值，也不主张自动换为 Docker 后端。

**裁决：**当前价值主张是完整且易用的授权/隔离闭环。未来移植需提供逐项安全能力映射，不支持的关键约束直接使编译失败；另开非等价配置则重新审查，不能用一条提示当成原样迁移成功。

### F12 / P1：原型演示与验收证据需彻底分开

**证据：**prototype.html 999–1016 的 CHECKS.map 固定输出 ✓；startReview 仅改介绍文字，权限仍为 Claude 示例；运行函数只显示 toast。已有 REVIEW 已诚实指出这些限制，PR 自述也没有功能测试。

**裁决：**这是原型，不应当作功能实现漏洞或造假指控；但标记改为“设计检查项/待验证”，固定数据标“演示数据”，禁止把该页面截图用作验收报告。真实验收必须关联应用包、镜像、代码 SHA、步骤与结果。

## 3. 对上一版方案的反向攻击

不能因为上一版是我写的，就把它当成已经成立的答案。

| #1 对上一版最有力的质疑 | 该质疑是否成立 | 最终处理 |
|---|---|---|
| 无网卡加预装依赖，可能只能跑漂亮样例，遇到真实仓库就无法安装/测试 | 成立；这是功能交付风险 | 用一份有真实测试的目标项目验证；版本化工具链和依赖准备作为明确产品功能；首版不承诺任意在线安装，不把限制藏起来 |
| 上一版说独立连接器，但没有具体解释 stdio 密码/HMAC/SSH 如何兼容 | 成立 | 连接器按认证机制分类；支持可代签/可代理者，不能适配者明确缺口；不把独立 VM 当成恶意秘密持有者不会泄密的证据 |
| 导入副本对大仓库慢、导出新目录不如直接回写顺手 | 成立 | 首版以不覆盖原项目换确定性；有大小/数量预检、进度、差异；优化复制或冲突回写后续单列 |
| 只有工程架构不足以让用户理解授权、撤销和安全收益 | 成立，#1 在这一点更完整 | 采用 #1 的后果描述、审批快照、账户连接和活动记录，收敛为少数页面 |
| 无网卡并不等于阻止已授权渠道泄漏数据 | 成立；上一版已有此限制，但产品仍需显式呈现 | 首次授权提示文件可能发送至所选模型/服务；不宣传完整 DLP |
| 一个独立 reviewer Agent 不能保证测试真实或审查独立可靠 | 成立 | 独立上下文只是审查手段；最终以真实执行证据、变更差异和维护者门禁为准 |

上一版已经包含审批绑定、上游结果未知、终端输出不可信和多类 MCP 方法限制，不应把这些已有设计重新包装成对上一版的“新修复”。本次主要把其接口、信任域与产品交互落为确定性决策。

## 4. 两版正面对抗后的取舍

| 议题 | #1 较强之处 | 上一版较强之处 | 最终决定 |
|---|---|---|---|
| 用户体验 | 后果解释、措辞快照、权限变化展示 | 首次完整主流程比较简单 | 保留 #1 的解释与快照，删掉非首版页面和重复授权 |
| 凭据 | 兼容动机与凭据入口较完整 | 不向 Agent 交出原始秘密 | 严格模式；不用隐式原始凭据兜底换“兼容” |
| 隔离 | 将 MCP 视为独立对象 | 无网卡、无共享目录、明确 guest root 假设 | 两点结合；独立信任域采用独立 VM，必要时承认同域 |
| 授权 | Policy/Workload/界面有初步建模 | 单次操作参数绑定、停止撤权较明确 | 统一授权交集、RunGrant、PendingAction、可信主体身份 |
| 文件 | CoW 最终体验更顺滑 | 副本+新目录导出更易验证 | 首版采用副本；不是否定后续 CoW，而是先落实语义 |
| 审计 | 展示和追溯更完整 | 验收证据更严格 | 保留 UI，改为有来源等级的事件，不声称完备监控 |
| 兼容 | 追求广度 | 不假装未知模式已经可用 | 独立兼容矩阵，三 Agent 全部保留，MCP覆盖逐项核实 |
| 排期 | 中长期产品故事充分 | 更贴近比赛垂直交付 | 当前只做安全工作台；云生产/预热池/持久化不进入首版 |

这不是把两份文档拼接。最终基线由 FINAL_SPEC.md 单独定义；冲突时不再同时遵循两个不同版本。

## 6. PR 处理建议

保留 source/ 下的原始资料及已有 REVIEW，作为设计输入和讨论证据。新增最终规格并将 README 的当前实施基线指向它，显式标明旧资料“历史设计，不作为冲突处的实现依据”。不要倒改原始资料以制造“从来没有矛盾”的历史。

先由维护者确认本次安全决策，再把核心契约、验收 fixture 和最小工程骨架纳入小 PR；不要把一套尚未验证的产品一次性生成进主分支。

“闭源免费”的产品假设与仓库许可证需由维护者统一；本轮不更改许可证，不代替团队作商业或法律决策。

官方技术参考及所有源文件入口见 SOURCES.md。详细验收与里程碑见 ACCEPTANCE.md、ROADMAP.md；它们是规格，不是已运行的测试程序。
