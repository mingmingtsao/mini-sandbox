## 1. 产品定位

### 1.1 一句话定义

**一款面向 AI Agent 开发者的 macOS 桌面应用，以零权限启动、运行前审查、宿主凭据保管和代码副本编辑支持 claude code、codex、dsh 等 Agent 的适配场景，并将本地策略导出用于生产部署。凭据接入须有明确适配器，各目标兼容性以验证结果为准。**

### 1.2 核心价值的三层拆解

核心价值是"图形化的桌面级安全沙箱"，但这句话对工程师没有约束力。拆成三条可验收的断言：

| 层次 | 断言 | 验收方式 |
|---|---|---|
| **能跑** | 以 claude code / codex / dsh 为目标，按已配置 Provider 或已验证专用适配器接入；不承诺任意现成 CLI 无需改造 | 待逐款验证"读代码→修改副本→跑测试→调外部 API→确认回写"闭环，未验证的接入不得标为支持 |
| **够安全** | Agent 在沙箱内无法触及未显式授予的文件、网络、秘密 | 红队用例：Agent 尝试读取 `~/.ssh`、访问未授权域名、dump 环境变量，均被阻断且留证 |
| **凭据接入** | 用户在宿主连接账号，工作负载配置仅含引用；代理模式原始凭据不进 guest，引用模式须单独批准明文交付 | 验证已配置 HTTP Provider 的代理路径；自定义目标须先验证 fd 适配器；数据库、SSH 和任意 CLI 不列为默认支持 |

### 1.3 目标用户与典型场景

**主用户：Agent 开发者**（个人开发者 / 小团队技术负责人）

| 场景 | 用户当下的做法 | 痛点 | 本产品的介入点 |
|---|---|---|---|
| 让 claude code 在真实仓库上自主改代码 | 直接在本机跑，或 `--dangerously-skip-permissions` | Agent 有本机全部权限，误删/误推/泄露凭据无法挽回 | 仓库以宿主只读基础快照 + guest 可写副本提供，三方差异经确认后才回写宿主 |
| 装一个第三方 MCP server | 复制一条 npx 命令到配置里 | 不知道它能连哪、能读哪、拿了什么凭据 | 运行前展示其完整可达范围，用户点"信任"才启动 |
| 跑 Agent 需要调 Claude API / GitHub | 在 `.env` 或 shell profile 里放明文 key | key 进了磁盘、进了 Agent 上下文、可能进日志 | 已配置的 HTTP Provider 采用宿主代理注入，原始凭据不进 guest；具体客户端兼容性待实测 |
| 本地验证完想上生产 | 重写一套 K8s NetworkPolicy + Secret | 本地策略和生产策略两套，漂移无人发现 | 同一份 policy 源文件编译出两种产物 |

**次用户（设计时需兼顾，不排期）：团队技术负责人**——需要把一份策略下发给团队成员。这是未来付费版的抓手，本期只保证"策略文件可导出、可被他人导入"，不做集中管控。

### 1.4 不做什么

明确划出边界，避免后续需求蔓延：

- ❌ 不做通用虚拟机管理器（不与 UTM / Parallels 竞争）
- ❌ 不做容器开发环境（不与 Docker Desktop / OrbStack 竞争）
- ❌ 不做 Agent 本身的能力增强（不做 prompt 管理、不做模型路由）
- ❌ 不做企业级集中管控（本期；留接口）
- ❌ 不做 Windows / Linux 的完整体验（本期；只在架构上留抽象层）

## 2. 五个关键决策的落地选择

这一节是全文的地基。后续所有模块、接口、界面设计都必须显式回指本节。

### 决策一：秘密采用「引用模型 + 代理注入」双轨

**选择：以 `proxy-inject` 为默认设计路径；`memory-inject` 是需要单独明确授权、且目标有已验证适配器的例外。系统不因代理不可用而自动切换模式。**

| 秘密的使用方式 | 模式与准入 | 支持边界 |
|---|---|---|
| 作为 HTTP 认证头发往已配置 Provider（如 Anthropic、OpenAI、GitHub API） | `proxy-inject`：宿主代理认证 | 原始凭据不进 guest；这是设计路径，Provider 与客户端的兼容性待实测 |
| 自定义服务，目标原生支持读取 fd 或有已验证专用 fd 适配器 | `memory-inject`：单独审查并明确批准明文交付 | 仅提供有明确适配器的目标；用户进程会得到明文 |
| 数据库连接串、SSH、任意 CLI | 不默认支持 | 未验证、仅支持 env/argv 或磁盘文件的接入一律阻断；不自动降级，不承诺现成 CLI 无需改造 |

**模式选择与审查**：用户先选择服务与目标程序。系统仅展示有明确适配器的接入方式，并在能力审查中说明模式。`proxy-inject` 不可用时阻断；改选 `memory-inject` 必须先通过目标适配验证，再单独展示“该程序会获得密钥明文；如果被攻陷，可能复制或外传”，经完整审查与批准记录后才可使用。网络授权仍单独裁决。

**🚫 否决条件**：
1. 产品不得将秘密明文写入沙箱文件、环境变量、启动参数、workload spec、普通 API 响应、日志或界面回显；spec 仅使用 `secretRef`，由宿主 Broker 解析。
2. `proxy-inject` 的原始凭据不得进入 guest。`memory-inject` 仅可交付给单独获准且有已验证适配器的目标进程，不得用“明文不进沙箱”描述该模式。
3. 用户不得被要求在沙箱内填写敏感信息；未验证的接入方式不得以 env、argv 或文件绕过。

**凭据交付与生命周期**：

1. 用户在宿主原生 UI 连接账号或导入凭据，保管库写入 macOS Keychain（`kSecAttrAccessibleWhenUnlocked`，ACL 绑定本应用代码签名），使用后清零产品受控缓冲区。
2. `proxy-inject`：宿主在每次代理认证前检查授权及凭据撤销、过期状态，Broker 解析后由宿主代理注入认证头，原始凭据留在宿主。
3. `memory-inject`：宿主按 `runId`、`workloadId`、进程启动标识 `processStart`（含不可复用的 `launchId`）和 `secretRef` 共同核验授权、模式及适配器，不能仅凭可复用 PID 或 guest 自报身份下发。经 vsock 将凭据交给 guest 可信启动器，由启动器通过一次性匿名 pipe 的继承 fd 交给指定目标进程。匿名 fd 不是文件路径；目标必须原生支持读取 fd，或通过已验证专用适配器读取，不经 env、argv 或落盘传递。
4. 启动器仅对本次 `exec` 的显式 allowlist 开放所需 fd 继承，其余 fd 设置 `close-on-exec`。读完即关闭凭据 fd，非必要子进程不得继承。`mlock`、禁 swap/core 与清零仅约束产品受控缓冲区；第三方程序取得明文后的内存副本、日志或外传无法由此保证不泄漏。
5. 撤销或过期后，宿主停止后续代理认证及新凭据交付。已交付的引用凭据无法回收；系统终止持有该凭据的相关运行，并提示用户在服务端执行必要轮换。终止不能收回已经复制或外传的凭据。

`⚖️ 取舍`：代理模式减少 guest 接触原始凭据的机会；引用模式扩大可适配目标范围，但目标进程必须持有明文。以已验证适配器和单独授权限定这项例外，不把第三方进程内存保护作为产品保证。

### 决策二：姿态采用「硬隔离边界 + 零权限启动」混合模型

**选择：用 Apple Virtualization.framework 建立 microVM 硬边界，在边界之上由宿主 Broker 实施零权限启动与按需授予。**

这是本产品与 Cosmonic Desktop 的**根本分野**，必须说清。

```
┌─────────────────────── 宿主 macOS ───────────────────────┐
│                                                           │
│  用户原生 UI ── 能力审查 / 秘密录入 / 审计查看            │
│       │                                                   │
│  ┌────┴──────────────────────────────────┐               │
│  │  Capability Broker（宿主守护进程）     │ ← 唯一裁决点  │
│  │  · 持有 Keychain 访问权                │               │
│  │  · 持有文件系统授权（Security-Scoped） │               │
│  │  · 运行出站代理（TLS 终止 + 头注入）   │               │
│  └────┬──────────────────────────────────┘               │
│       │ vsock（唯一通道，无共享内存/无网络栈直连）        │
│  ┌────┴──────────────────────────────────┐               │
│  │        microVM（Virtualization.fw）    │               │
│  │  ┌──────────────────────────────────┐  │               │
│  │  │ guest Linux（极简，无 SSH 无 shell 服务）│          │
│  │  │  · 网络：默认无路由，仅 vsock      │  │ ← 零权限起点│
│  │  │  · 文件：默认空 rootfs + tmpfs     │  │             │
│  │  │  · 秘密：默认无                    │  │             │
│  │  │  ┌────────────┐  ┌──────────────┐ │  │             │
│  │  │  │ Agent 工作负载│  │ MCP 工作负载 │ │  │             │
│  │  │  │ (claude code)│  │ (独立进程组) │ │  │             │
│  │  │  └────────────┘  └──────────────┘ │  │             │
│  │  └──────────────────────────────────┘  │               │
│  └────────────────────────────────────────┘               │
└───────────────────────────────────────────────────────────┘
```

**两套叙事如何并存且不矛盾**：

| 面向 | 使用的叙事 | 在界面中的体现 |
|---|---|---|
| 对"会不会伤到我的电脑" | **硬隔离**："它在一台独立的小电脑里，出了事也碰不到你的 Mac" | 首次启动引导、出错时的安抚文案 |
| 对"它能干什么" | **零权限**："它启动时什么都碰不到，你给什么它才有什么" | 能力审查界面、权限清单 |

`⚖️ 取舍`：
- **为什么不是纯 Wasm 组件模型（Cosmonic 路线）**：核心价值白纸黑字要求支持 claude code / codex / dsh。这些是完整 POSIX 程序，依赖 fork/exec、文件系统语义、原生 node/python 运行时。要跑在 Wasm 组件模型里需要用户重新编译整个工作负载——这与核心价值直接冲突。**这一条是否决性的，不是权衡**。
- **为什么不是纯容器做减法**：容器共享宿主内核，逃逸面大；更关键的是"继承权限后做减法"的叙事对非技术用户无法解释——"我默认有你全部权限，但我保证减掉了危险的部分"，这句话无法建立信任（违反锚点 1）。
- **混合模型的代价**：microVM 启动开销（见决策五）、宿主与 guest 两侧都要实现策略执行、网络需经代理导致部分协议受限。

**🚫 否决条件**：`proxy-inject` 的原始凭据不得进入 guest；`memory-inject` 仅按 D1 的单独授权与已验证适配器交付。guest 的网络出口默认为空，每个可连接主机必须显式进入 allow-list；凭据授权不自动授予网络访问权。所有能力未授权默认拒绝，显式拒绝优先于允许，风险等级不产生授权。

### 决策三：能力审查严格发生在运行之前

**选择：运行前审查，且审查界面不含技术术语。**

**审查的触发时机**（三者任一）：
1. 首次运行某工作负载
2. 工作负载请求的能力集发生变化（指纹变更）
3. 运行中发生越界尝试，用户选择"补充授权"；该能力保持阻断，直到完整审查和批准记录完成

**界面语言的翻译规则**——这是本决策能否落地的关键。右栏是唯一允许出现在审查界面的措辞：

| 技术事实 | 🚫 禁止出现的措辞 | ✅ 审查界面的措辞 |
|---|---|---|
| `allowedHosts: [api.anthropic.com]` | "主机名 allow-list" | "能联网访问：Claude 官方服务" |
| `allowedHosts: ["*"]` | "通配符出站" | "⚠️ 能访问互联网上的任何地方" |
| 挂载 `~/code/myrepo` rw，`copyOnWrite: true` | "读写挂载点" | "能读取并修改代码副本；写回原文件前会请你确认" |
| `secretRef: anthropic-key`，`mode: proxy-inject` | "秘密引用注入" | "能以你的身份调用 Claude；这项代理连接不会把原始密钥交给程序" |
| `secretRef`，`mode: memory-inject` | "内存注入" | "这个程序会拿到密钥明文；如果被攻陷，可能复制或发出去" |
| `spawn: allow` | "允许 fork/exec" | "能在沙箱内启动其他程序" |
| 无网络能力 | "出站策略为 deny-all" | "完全不能联网" |

**判断辅助**：每条能力旁标注风险等级（🟢 低 / 🟡 中 / 🔴 高），并给出一句话后果描述，例如 `🔴 能访问互联网上的任何地方 —— 如果这个程序被人动过手脚，你的代码可能被发出去`。等级只影响告知、展示和提示，不改变裁决：未授权默认拒绝，显式拒绝优先；低风险同样需要用户批准。补授必须完成完整审查并写入批准记录，随后才可生效；存在显式拒绝时，需在审查中明确修改该拒绝，新增允许不能覆盖它。

**🚫 否决条件**：
1. 审查界面不得要求用户理解任何技术术语即可做出信任判断。
2. 不得提供"全部允许"的一键按钮（可以有"按推荐配置运行"，但推荐配置的内容必须逐条可见）。
3. 首次授权须在工作负载启动前完成；运行中补授须在对应能力执行前完成完整审查和记录。

`⚖️ 取舍`：运行前审查增加启动操作。为减少重复审查，同一工作负载、同一能力指纹可复用仍有效的批准记录；撤销、过期或命中显式拒绝后不得沿用。审查结果可导出为策略文件，导入后仍须完成本地审查。

**普通代码编辑与宿主回写**：工作目录默认 `rw`，且必须为 `copyOnWrite: true`；显式 `false` 拒绝。宿主提供运行基线的只读基础快照，guest 仅修改可写副本，不支持未经确认直接写宿主。运行授权不等于回写批准。

回写比较运行基线、当前 host 和 guest 修改的三方 diff，覆盖内容修改、添加、删除、重命名与二进制文件。用户选择批次后，任一冲突阻断整个选定批次；用户可取消、解决冲突后重新预览审查，或明确确认覆盖当前预览中哪些选定文件与冲突。覆盖不沿用旧批准，范围或版本变化须重新预览确认，且不能绕过禁止路径或符号链接逃逸检查。

同意绑定本次所选操作的 diff digest 和 host 版本，并冻结本次待提交的 guest 内容。提交前，执行器必须在覆盖校验与实际写入的受控临界区重新校验；本次 diff、待提交 guest 快照或 host 版本再有变化，即使已有批准也立即使确认失效，重新展示差异并审查，不静默覆盖。运行中的后续编辑不能替换冻结内容。路径与符号链接检查同样在此边界执行，并须检测外部写入竞争；仅有产品内部锁不构成保证，无法保证时停止提交。若批次执行中部分失败，停止余项并逐项报告已成功、失败与未执行项，不显示“全部成功”；保留基线和 guest 副本供重试，重试按当前 host 重新审查。

### 决策四：MCP 服务器是一等公民

**选择：MCP server 作为独立工作负载运行，与调用它的 Agent 相互隔离。**

这是本产品最锋利的差异点。竞品把 MCP 当作"Agent 的配置项"，我们把它当作**独立的不可信代码**。

| 设计要点 | 具体规格 |
|---|---|
| 进程边界 | 每个 MCP server 独立进程组，独立 PID/mount/net namespace，不与 Agent 共享文件系统视图 |
| 启动姿态 | 无任何对外网络访问；每个目标主机显式 allow-list |
| 与 Agent 的通信 | 只经由 Broker 转发的 stdio/JSON-RPC 通道，Agent 无法直接访问 MCP 进程 |
| 秘密 | MCP 凭据按 D1 使用 `proxy-inject` 或经单独批准的 `memory-inject`；系统不向 Agent 直接交付。引用模式下 MCP 会获得明文，无法保证被攻陷的 MCP 不向外复制或传递 |
| 审查粒度 | 单个 MCP server 单独审查，不随 Agent 一起批准 |
| 工具级可见性 | 审查界面列出该 MCP 暴露的工具清单（`tools/list` 结果），用户可逐个工具开关 |

**工具级开关是本设计的独有项**：用户可以批准一个 GitHub MCP 的"读 issue"但拒绝"创建 PR"。这在协议层通过 Broker 过滤 `tools/list` 响应与拦截 `tools/call` 实现。

`⚖️ 取舍`：工具级开关增加了 Broker 的协议理解成本（需跟进 MCP 协议版本演进），也可能让某些 MCP server 在工具被部分禁用时行为异常。但"MCP 是一等公民"这个承诺如果只做到进程隔离，和竞品没有区别——隔离进程容易，理解它要做什么才难。

### 决策五：一次性沙箱是默认实践，并为此设定硬性开销预算

**选择：默认每次运行使用全新沙箱，并把启动开销当作产品指标而非工程指标来管理。**

**开销预算（设计假设，需工程验证；未达标则降级策略如下）**：

| 指标 | 目标值 | 未达标时的降级方案 |
|---|---|---|
| 冷启动（首次，含镜像加载） | ≤ 3s | 允许，仅首次 |
| 热启动（预热池命中） | ≤ 800ms | 若 >2s，默认改为"会话级复用" |
| 常驻内存（空闲预热池，2 个实例） | ≤ 512MB | 若超，预热池降为 1 |
| 单沙箱内存基线 | ≤ 256MB | 若超，放弃预热池 |

**预热池机制**：应用启动后在后台预创建 N 个"已启动但未授予任何能力"的空白 microVM。用户点"运行"时，从池中取一个，注入能力，挂载文件。因为零权限启动，**空白实例是完全同质的**，可以安全复用——这是决策二反过来支撑决策五的地方。

**三种生命周期模式**（用户可选，默认第一种）：

| 模式 | 行为 | 适用场景 | 界面措辞 |
|---|---|---|---|
| **一次性**（默认） | 每次运行全新沙箱，退出销毁运行环境；待确认或失败回写的基线和 guest 副本单独保留，直到用户完成回写或明确丢弃 | 跑不信任的代码、试新 MCP | "用完即焚（推荐，未处理改动保留待确认）" |
| 会话级 | 同一次工作会话内复用，关闭窗口销毁运行环境；未处理改动与基线继续保留 | 连续调试、需要保留 node_modules | "本次工作期间保留" |
| 持久 | 沙箱状态落盘，跨重启保留 | 长期项目的固定环境 | "长期保留（风险更高）" |

**🚫 否决条件**：持久模式不得成为默认；选择持久模式时必须展示其安全含义（"沙箱内的程序改动会一直留着，包括你没注意到的"）。

`⚖️ 取舍`：一次性沙箱对 Agent 开发体验有真实摩擦——每次重装依赖。缓解手段是**分层缓存**：依赖层（node_modules、pip cache）作为只读层缓存在宿主，跨沙箱共享但不可写。这保留了"干净启动"的语义，同时避免重复下载。代价是缓存层本身成为一个需要校验的信任边界（缓存投毒风险），需在设计中单列（见 02 模块设计）。

## 3. 竞品分析：Cosmonic Desktop（按六问透镜）

> 事实来源：Cosmonic 官方博客。标注"推断"的为基于公开信息的判断，非官方表述。

| 透镜 | Cosmonic Desktop | 本产品 | 差异的产品含义 |
|---|---|---|---|
| **1. 假设用户运行什么代码** | Wasm 组件——即为该模型重新编译过的代码。官方定位为"让 AI Agent 执行它生成的代码" | 以 claude code、codex、dsh 等 POSIX 程序为适配目标；凭据接入与运行兼容性须逐项验证 | 本产品以现成 Agent 的运行需求为起点，凭据适配不承诺任意 CLI 无需改造 |
| **2. 安全承诺是阻断还是限制** | **限制**——"没有授予的能力不存在"（ambient authority 是它批判的对象） | **阻断 + 限制**——VM 边界负责阻断，Broker 负责限制 | 它的叙事更优雅但依赖用户理解"能力"概念；我们多一层"物理隔离"的直觉解释，对非技术用户更易建立信任 |
| **3. 本地到生产的路径** | 短——同一 Wasm 工件可投递到团队已运维的基础设施 | 中——policy 为源，编译出 OCI manifest（通用轨）或云主机投递包（增强轨） | 它在统一工件上占优；我们在"不要求用户换运行时"上占优 |
| **4. 秘密如何交付** | 声称隔离于"你的密钥"，但公开信息未说明密钥如何进入系统（推断：仍需某处录入） | 宿主保管；代理模式原始凭据不进 guest，引用模式经单独授权向适配目标交付明文 | 按模式验收交付边界、用户告知和适配器准入 |
| **5. 对 MCP 是隔离还是放行** | 隔离 + **运行前可见**（"See exactly what an MCP server can reach before it runs"）——与我们的决策三、四同向 | 隔离 + 运行前可见 + **工具级开关** | 方向一致，我们在粒度上再进一步。工具级开关是可防御的差异点 |
| **6. 开源/闭源服务什么商业逻辑** | 免费、纯本地、无需登录；建立在开放标准上（wasmCloud 生态）。推断：桌面端为 Cosmonic 云平台的生态入口 | 闭源免费，为自家云主机/Agent 产品线引流 | **商业逻辑高度同构，但我们少了开源生态这张牌**。见 §4 风险 |

### 3.1 与 Cosmonic 的正面交锋点

**它比我们强的**：
1. 工件统一性——Wasm 组件从本地到生产零重写，我们需要编译步骤
2. 开源生态——建立在开放标准上，有社区杠杆
3. 资源开销——Wasm 实例启动成本远低于 microVM，一次性沙箱的激进程度它能做得更彻底
4. 跨平台——已在三平台公测，我们本期只做 macOS

**我们比它强的**：
1. **兼容性目标**：面向 POSIX Agent，无需改成 Wasm 组件；具体客户端和凭据接入仍需验证
2. **秘密交付边界**：按代理模式与单独授权的引用模式分别验收
3. **MCP 工具级粒度**
4. **隔离的直觉可解释性**——"独立的小电脑"比"能力模型"好讲

### 3.2 云产品沙箱的计费对比

本产品桌面端免费，引流目标是云侧 Agent 运行。定价设计（05）需补齐以下竞品云侧定价数据及官方来源：

| 需核实项 | 用途 |
|---|---|
| AWS Bedrock AgentCore 的 Code Interpreter / Browser Tool 计费维度与单价 | 云侧 Agent 沙箱定价锚点 |
| 阿里云函数计算 / 无影 的 Agent 沙箱类产品计费 | 国内定价锚点 |
| 腾讯云 Cloud Studio / SCF 的同类能力计费 | 国内定价锚点 |
| 各家是否对"沙箱空闲时间"计费 | 决定我们"预热池"在云侧的成本模型 |

上述数据作为 05 定价设计的输入。

## 4. 设计风险与边界

| # | 风险 | 性质 | 缓解设计 | 残余风险 |
|---|---|---|---|---|
| R1 | **闭源 + 无开源生态**，面对 Cosmonic 的社区杠杆处于守势 | 商业 | 以"开放策略格式"替代"开源代码"：policy schema 与导出工件格式公开且有规范文档，允许第三方生成/消费 | 社区贡献无法流入核心，生态增速受限 |
| R2 | **microVM 开销**使一次性沙箱默认值无法成立 | 技术 | 预热池 + 分层缓存；设定降级阶梯（决策五表格） | 若热启动 >2s，产品的核心安全默认值被迫退让，需重新评估 |
| R3 | **依赖缓存层投毒**——为缓解摩擦引入的共享只读层成为攻击面 | 安全 | 缓存层内容寻址 + 校验和；缓存仅只读挂载；缓存写入只能由宿主 Broker 在验证来源后执行 | 上游包本身被投毒时我们无法识别 |
| R4 | **TLS 终止代理**需在 guest 内安装自签 CA，等于在沙箱内建立了一个信任锚 | 安全 | CA 私钥仅存宿主 Keychain；代理只对 allow-list 内主机终止；对未 allow-list 主机直接拒绝而非放行 | 若 guest 内程序主动信任该 CA 并被诱导，存在中间人误用空间 |
| R5 | **Agent 被 prompt 注入**后主动滥用已授予的合法能力 | 安全 | 能力最小化；未授权请求阻断后完整补授；宿主回写三方 diff 确认；全量审计 | 已授予范围内仍可能滥用；引用凭据交付后可被目标进程复制或外传 |
| R6 | **用户对审查界面疲劳**，形成无脑点"信任"的习惯 | 体验 | 风险分级 + 高风险项需额外动作（不能与低风险项一起批量确认）；同指纹仅复用仍有效批准 | 疲劳是长期趋势，需靠埋点监测"审查停留时长"并迭代 |
| R7 | **macOS 单平台**导致团队场景无法闭环（成员平台不一） | 范围 | 策略文件平台无关，可被未来版本的其他平台客户端消费 | 本期团队场景事实上不可用 |
| R8 | **审计日志本身含敏感信息**（访问过的主机名、文件路径） | 隐私 | 日志仅存本地，默认不上传；导出时提供脱敏选项；日志中秘密一律以引用名呈现 | 本机被攻破时日志成为侦察资源 |

### 4.1 权限矩阵（宿主侧主体 × 资源）

| 主体 | Keychain 明文 | 宿主文件系统 | 网络出站 | 审计日志 | 策略文件 | guest 内存 |
|---|---|---|---|---|---|---|
| 用户（原生 UI） | 写入、删除（**不可读取已存明文**） | 通过系统 Picker 授权 | — | 读 | 读写 | — |
| Capability Broker | 读（仅使用时，不回显） | 按 Security-Scoped Bookmark 读取快照；确认并复验后回写 | 代理出站，按 allow-list | 写（仅追加） | 读 | 仅按 D1 绑定目标交付 `memory-inject` |
| 出站代理进程 | 读（仅注入用凭据） | 无 | 按 allow-list | 写（仅追加） | 读 | 无 |
| guest 内工作负载（Agent） | 无 Keychain 访问权；获准 `memory-inject` 时收到对应明文 | 无直接宿主写权限（仅见只读基线与可写副本） | 无（仅经 Broker 代理） | 无 | 无（仅见自身能力摘要） | 自身 |
| guest 内 MCP 工作负载 | 无 Keychain 访问权；获准 `memory-inject` 时收到对应明文 | 无直接宿主写权限（独立视图） | 无（独立 allow-list） | 无 | 无 | 自身 |

**关键不变式**：
- 用户自己也**不能**从本产品 UI 中读回已存入的明文秘密（只能覆盖或删除）。这牺牲了一点便利，换来"UI 不是秘密的泄露面"。
- Agent 与 MCP 的文件系统视图、网络 allow-list、秘密集合**三者均不交叉**，除非用户显式建立桥接。

### 4.2 数据泄露风险点清单

| 泄露面 | 具体路径 | 设计对策 |
|---|---|---|
| 配置文件 | 用户把 key 写进 workload spec | schema 层面拒绝明文字段；UI 检测到疑似密钥格式时阻断并引导至秘密录入 |
| 日志 | 凭据被记入请求日志 | 代理层对已知认证头做结构化脱敏；日志写入前过滤 |
| Agent 上下文 | 目标进程读取或复制 key | `proxy-inject` 原始凭据不进 guest；`memory-inject` 经匿名 fd 交付，不经 env/argv/文件；目标获得明文后仍可能复制或外传 |
| 产物导出 | 沙箱内产物带出 `.env` 等文件 | 导出前扫描，命中敏感模式时逐项确认 |
| 崩溃转储 | 内存副本进入转储或 swap | 产品受控缓冲区使用 mlock、禁 swap/core 并清零；不保证第三方程序持有的明文副本不泄漏 |
| 剪贴板 | guest 与宿主共享剪贴板 | 默认不共享；开启需显式授权且单向 |
| 审计日志导出 | 分享日志给他人时带出内网主机名 | 导出脱敏选项（主机名哈希化、路径截断） |

## 5. 本批设计决策速查表

供后续文档与评审引用：

| 编号 | 决策 | 一句话 |
|---|---|---|
| D1 | 秘密模型 | `proxy-inject` 原始凭据不进 guest；`memory-inject` 为单独明确授权且有已验证 fd 适配器的明文交付例外，不自动降级 |
| D2 | 隔离姿态 | microVM 硬边界 + Broker 零权限启动；对外两套叙事（伤不到你 / 默认什么都不给） |
| D3 | 审查时机 | 未授权拒绝、显式拒绝优先；风险仅影响告知；补授完整审查并记录后生效；工作目录 rw 强制 CoW，回写另行按三方 diff 确认并复验 |
| D4 | MCP 地位 | 一等公民，独立工作负载，与 Agent 互不可见，支持工具级开关 |
| D5 | 生命周期 | 一次性为默认，预热池保障开销，分层缓存缓解摩擦，持久模式不得为默认 |
| D6 | 生产路径 | policy 为源文件，OCI manifest 为通用产物，云主机投递包为增强产物 |
| D7 | 平台范围 | macOS 深度优先，跨平台仅留抽象层，策略文件平台无关 |
| D8 | 商业模式 | 闭源免费，为云产品线引流；开放策略格式替代开源代码 |
